# Defect register

Defects found while building and redesigning the workbench interface, with how each was found, what was done, and how the fix is verified. Severity: **critical** (wrong or misleading result, or the page unusable), **high** (a feature or a guarantee broken), **medium** (degraded but usable), **low**.

"Found by" says whether a person looking at the page, a test, or the automated visual QA caught it. Open items are at the top.

## Findings that are not defects

| Finding | Explanation |
|---|---|
| Making a failed database "multi-zone" does not help when the database itself is marked down. | In this model a direct "down" is loss of the whole component; redundancy protects against losing a zone. So after a direct failure the recovery options offered are a standby and circuit breakers, and after a zone failure, redundancy. Each option is previewed and dropped if it improves nothing. |
| "Max load" can be limited by a queue consumer, not only by the request path. | The figure is the entry load at which the first component reaches its capacity. For a queue consumer that means the queue grows without bound. The tooltip names the limiting component. |
| With circuit breakers, "requests answered" stays near 100% while a database is down. | A breaker lets callers answer without the failed dependency, so requests are answered but degraded. The comparison table says "answered counts requests that get any answer, including a degraded one", and "components affected" is shown beside it. |
