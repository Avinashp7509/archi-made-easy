# Archi-Made-Easy: program plan

Status: approved 2026-11-10, with the product-vision amendments below. This file is the single source of truth for scope and phase order. The approved technical design (schema extensions, simulation formulas, review rules, viewer design, testing strategy) is in [BASE-DESIGN.md](BASE-DESIGN.md), and every part of it still applies unless this file overrides it. Progress and evidence are tracked in [CHECKLIST.md](CHECKLIST.md).

## 1. Product identity

- **Name.** Archi-Made-Easy. Skill identifier `archi-made-easy`. JavaScript namespace `ArchiMadeEasy`. Files, folders, packages, commands and the release archive use `archi-made-easy`. Environment variables use `ARCHI_MADE_EASY_`. HTML template markers use `ARCHI_MADE_EASY:`.
- **Origin.** The product is derived from an Apache-2.0 project (upstream repository and commit are recorded in `NOTICE`, `ATTRIBUTION.md` and the import commit). Upstream copyright lines, licence texts and third-party notices are kept verbatim. The upstream name appears only in those attribution files.
- **Ownership.** Copyright for new work: Avinash Roy. The GitHub owner is a single placeholder (`OWNER`) held in `archi-made-easy/skill-release.json`. The release check fails while it is unset; ordinary tests do not.
- **History.** The repository starts fresh with one import commit of upstream `11b0d60`. Upstream history is not carried.
- **Method.** The migration is dependency-aware, not blind text replacement:
  - A reviewed mapping table and a migration script rename paths with `git mv` and rewrite identifiers by context: JS identifier, prose, environment variable, marker, URL.
  - Generated files (validators, template, goldens, gallery, zip) are regenerated by their own generators, never text-edited.
  - A guard test fails if the old name appears in any tracked file outside the attribution allowlist.
- **Inventory first.** Upstream-project records that are not product capabilities are listed in `docs/program/IDENTITY-INVENTORY.md`, each with a keep, rename or retire decision and its test dependencies. Examples: journal, review evidence, contributor cards, star history, upstream-published integrations, the upstream changelog. Nothing that is a working capability is retired.
- **Inherited diagrams stay valid.** Documents written for the upstream product validate and render unchanged. Any upstream-named field or URL they contain is accepted as a legacy alias.

## 2. Global skill distribution

- `archi-made-easy/SKILL.md` follows the Agent Skills format:
  - `name`, `description`, `license`, `compatibility`, `metadata`;
  - progressive disclosure into `references/`, `schemas/`, `scripts/`, `assets/`, `examples/`, `evals/`;
  - at most 160 lines (the inherited limit is kept).
- Deliverables:
  - a portable, deterministic release ZIP;
  - a zero-dependency installer `install.mjs` (agent and scope selection, `--dry-run`, `--uninstall`);
  - per-agent install instructions, a compatibility matrix, example prompts and troubleshooting;
  - a release workflow and automated packaging and installation tests.
- Every compatibility row states its evidence level:
  - **Exercised:** the agent loaded the skill and produced an artifact.
  - **Placement verified:** files installed where the agent documents it reads skills.
  - **Documented only:** not tested.
- No agent is claimed beyond its evidence level.
- Agent entrypoints: root `AGENTS.md` section, `.github/copilot-instructions.md`, `.github/agents/architect.agent.md`, `.cursor/rules/archi-made-easy.mdc`. All are thin pointers to `SKILL.md`.

## 3. Natural language first

- Users speak plainly; the agent writes the JSON. `SKILL.md` routes each request to one of these intents:

  | Intent | Example |
  |---|---|
  | create | "HA e-commerce on Azure" |
  | review | "identify risks" |
  | what-if | "what if the database fails", "20x traffic" |
  | optimise | "lower cost" |
  | from-repository | "diagram my repo" |
  | from-document | "from my requirements document" |
  | compare | "compare these two options" |
  | export | "give me draw.io / Mermaid / an RFC" |
  | explain | "explain this architecture" |

- Each intent has a playbook in `references/intents.md`: which questions are critical, which defaults to assume, which commands to run, and how to report.
- The agent asks only for information that changes the architecture materially, at most three questions at once. Typical examples are the cloud provider when it is not stated, the scale target, and hard compliance needs. Everything else is assumed and listed under "Assumptions" in the artifact and in the reply.
- New CLI support for the agent, so it never hand-computes:
  - `scaffold` starts from a pattern and provider pack;
  - `simulate --summary` and `review --summary` produce plain-language results;
  - `requirements` holds non-functional targets taken from a document or the conversation. Review checks the design against them: SLA target vs. composite SLA, budget vs. cost, RPO/RTO vs. DR settings.

## 4. Capabilities

The inherited capability set is the minimum baseline: 10 diagram types plus explainer, rendering, interaction, navigation, validation, the 9 quality gates plus the browser gate, existing exports, and base/head comparison.

Added on top, as designed in BASE-DESIGN.md:
- ARB scorecard
- component inspection (the Passport's Operational section)
- chaos scenarios and propagation
- traffic and capacity
- latency and availability
- security and trust boundaries
- FinOps
- C4 drill-down
- FMEA
- ADRs
- multi-format export

New in this amendment:
- **Before/after comparison.** `compare` gains operational and KPI deltas (SLA, P99, cost, max RPS, ARB score, findings opened and closed).
- **Alternatives.** Optional `workbench.alternatives` (named change sets) can be compared side by side inside the workbench.

## 5. Architecture intelligence layer

Versioned knowledge packs live in `archi-made-easy/knowledge/`, each with a `version` and `reviewed` date:

| Pack | Contents |
|---|---|
| `providers/{azure,aws,gcp,onprem}.json` | Service → role and component type, redundancy options. Published SLA only with a source URL and retrieval date; otherwise no number. |
| `patterns/*.json` | Reference architectures: web/HA, multi-region active-active, event-driven, microservices, data platform, zero-trust, AI/multi-agent, hybrid, migration landing zone. |
| `frameworks.json` | Framework identifiers and pillar mappings for Azure WAF, AWS WAF, Google Cloud Architecture Framework, NIST SP 800-207 and others. Each rule cites a framework section; no framework text is copied. |
| Rule registry | Each rule has `id`, `status` (`implemented` or `planned`), framework references, severity, and test fixture ids. |

- A generated `references/rule-coverage.md` shows exactly what is implemented. A test fails if an implemented rule lacks a passing and a failing fixture.
- Provider SLA values are fetched from official pages during Phase 3, each with URL and date. Unverified values are not shipped.
- Domains are covered by patterns plus rules. Any domain without rules is labelled "pattern only" in the coverage matrix.

## 6. Workbench experience

As in BASE-DESIGN.md Part 2.5, with these changes:
- The workbench is a flagship feature. It auto-opens when authored operational data exists, and `scaffold` output always contains such data.
- An alternatives comparison view is added.
- The agent opens the finalized HTML with the existing `open-artifact` path.
- Output is a standalone offline HTML file with no service dependency.
- Optional dependencies (a browser for visual checks and PNG/SVG export, ffmpeg for WebM) are detected by `doctor` and documented as optional.

## 7. Quality bar

- Requirements:
  - deterministic validation and builds, with typed and versioned schemas;
  - backward compatibility tests on all inherited examples;
  - unit, integration and browser tests;
  - cross-platform CI (Ubuntu, Windows, macOS) and per-agent installation tests;
  - a security review of viewer and CLI: injection into the data slot, the message bridge, iframe sandboxing, path handling;
  - golden examples and regression benchmarks (engine and render timings, model-quality floors).
- Every simulated number carries the label "modelled", and every input carries "authored" or "assumed". Nothing is presented as measured. No availability figure, price, provider capability or test result is invented.

## 8. Phases and order

Each phase ends with the inherited gate plus the phase's own tests, evidence recorded in CHECKLIST.md, and one commit.

| Phase | Scope | Exit criteria |
|---|---|---|
| 0. Baseline | Import upstream `11b0d60`, LF-pinned. Install development dependencies. Run doctor, validate on every example, `npm test`, `test:generated`, `test:full`, browser tests (Edge/Chrome). | `docs/program/BASELINE.md` records results; pre-existing failures are listed before any change |
| 1. Identity migration | Inventory; mapping table; migration script; path and identifier rename; regenerate all generated files; legacy aliases for inherited documents; identity guard test; NOTICE and ATTRIBUTION. | Same tests pass as at baseline; guard test passes |
| 2. Skill package and installation | SKILL.md rewrite (natural language first, ≤160 lines); `references/intents.md`; installer; release ZIP; agent entrypoints; install tests per agent into temporary homes; compatibility matrix. | Clean-environment install then `doctor` and `finalize` on an example pass from the installed copy |
| 3. Creation and rendering | Schema extensions (operational, requirements, alternatives, workbench); model and defaults; knowledge packs; `scaffold`; workbench data slot in rendering. | Old documents unchanged; scaffolded patterns finalize at showcase quality |
| 4. Review and simulation | sim, scenarios, review and rule registry, FMEA, cost, exporters, compare deltas; `review`, `simulate`, `export` commands; `--arb`. | Formula tests against hand-computed values; rule fixtures; receipts for old examples byte-identical |
| 5. Workbench | Viewer modes, ribbon, drawer, inspection, chaos, traffic, security, FinOps, C4, alternatives, handoff exports; engine parity test. | Browser tests and browser gate pass with workbench open and closed in both themes |
| 6. Showcase | Three flagships plus one scaffolded example per provider (Azure, AWS, GCP); regression benchmarks. | All finalize at showcase quality; benchmarks recorded |
| 7. Distribution readiness | Release workflow, CI matrix, docs, troubleshooting, security review, clean-environment acceptance, natural-language acceptance runs. | Acceptance tests in section 9 pass |

## 9. Acceptance tests (definition of done)

1. A fresh install from the release ZIP into an empty temporary home and project passes `doctor`.
2. From the installed copy only: `scaffold`, `finalize` (showcase quality), `review`, `simulate` (every preset) and `export` (every format) succeed on each flagship and each provider example.
3. Each finalized HTML opens offline, passes the browser gate, and its KPI ribbon equals `simulate --json` for the same inputs.
4. At least one real agent with the skill installed receives each of the nine example prompts in the product vision, and returns a valid interactive artifact or an evidence-based answer. Transcripts are recorded in `docs/program/acceptance/`. Agent runs are billed to you, so they run only after you confirm.
5. The identity guard, packaging, installation and cross-platform CI jobs pass.

## 10. Known constraints

- `ffmpeg` is not installed here, so the WebM-dependent rebuild (gallery live-proof) needs it installed or runs in CI.
- No agent CLI (`claude`, `codex`, `cursor-agent`) is on PATH here. Acceptance step 4 needs one installed or runs through the editor extension.
- The GitHub CLI is not installed, so publishing and release steps are prepared but not executed.
